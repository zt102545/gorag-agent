# “用途”改成“用”无法命中 QA：运行问题检测与优化方案

日期：2026-07-15  
环境：TestServer / Redis 7.4.7 / RediSearch 2.10.20

## 1. 问题

知识库已录入：

```text
单分镜改写功能有什么用途？
```

用户提问：

```text
单分镜改写功能有什么用
```

实际业务会话链路已经正常进入 QA 搜索，但没有返回这条 QA。

## 2. 现场证据

直接在 TestServer 的 `customer_service_qa` 索引执行 BM25：

| 查询 | BM25 结果 |
| --- | --- |
| `单分镜改写功能有什么用途？` | 精确命中目标 QA |
| `单分镜改写功能有什么用` | 0 条 |
| `单分镜` | 能找到目标 QA |
| question 字段中文三字片段 OR 查询 | 目标 QA 排名第 2 |

因此：

- 不是 QA 没有写入 Redis；
- 不是索引没有完成；
- 不是没有启用中文分词；
- 不是知识库录入或向量维度配置错误；
- 主要是中文 BM25 的普通整句查询采用 AND 语义，“用途”和“用”被处理成不同 token，只要其中一个 token 不匹配，整句就变为 0 条。

原先的向量通道仍可能召回语义相关问题，但它不能保证这个只差一个字的标准问法稳定排进最终 TopK。原 RRF 只使用两路名次，也没有利用“用户问句与标准问句只差一个字”这个强信号。

## 3. 已实施修复

### 3.1 保留严格 BM25

继续先执行原来的完整中文 BM25。完全一致或所有 token 都匹配时，它仍然是最高精度路径。

### 3.2 增加受控宽松 BM25

对包含中文、长度不少于 4 个字符的 query：

1. 去掉空白和标点；
2. 生成重叠的三字片段；
3. 最多保留 24 个片段；
4. 只在 `question` 字段做 OR 召回。

目标 query 会生成类似：

```text
@question:(单分镜|分镜改|镜改写|改写功|写功能|功能有|能有什|有什么|什么用)
```

限制在 question 字段、限制片段数量，可以扩大近似标准问法的召回，同时避免答案正文中任意常用字造成大范围噪声。

### 3.3 最终问句相似度重排

严格 BM25、宽松 BM25与向量结果去重融合后，再计算：

```text
1 - LevenshteinDistance(query, qa.question) / maxLength
```

只有编辑相似度不低于 0.6 才加重排分。这样：

- `用途` → `用`、少一个字、多一个语气词、标点差异会被稳定提升；
- 完全不同但语义相近的问法仍由向量排名负责；
- 不会把字符完全无关的结果仅凭宽松 OR 推到前面。

### 3.4 未修改意图路由

根据实际会话链路证据，该问题已经进入 QA 搜索，所以本次没有修改意图分拣策略，也没有用硬编码规则强制所有“功能问题”检索。

## 4. 验证结果

- Redis 现场严格 query：目标原句命中。
- Redis 现场变体 query：严格 BM25 为 0，宽松 BM25 能召回目标 QA。
- 单元测试确认编辑相似度重排后，`单分镜改写功能有什么用途？` 超过 `什么是单分镜剧本改写` 排到第一。
- `go test ./...` 全部通过。
- 已通过 `deployments/deploy-testserver.bat` 部署 TestServer。
- PM2 服务 online，健康检查返回 200，部署后没有 RedisSearch/索引错误。

## 5. 后续优化建议

### P1：增加检索可观测性

建议在会话 trace 中记录但不展示敏感正文：

- strict BM25 候选 ID/排名；
- relaxed BM25 候选 ID/排名；
- vector 候选 ID/排名与距离；
- RRF 分数、编辑相似度和最终排名；
- 被 knowledge base filter 排除的数量。

这样以后可以直接区分“没召回”“召回但排序低”“被知识库过滤”“命中后被质量判断拒绝”。

### P1：建立最小回归集

把标准 QA 自动派生为以下变体并持续评测 Top1/Top3：

- `用途` / `用` / `作用`；
- `如何` / `怎么`；
- `是否可以` / `能不能`；
- 去标点、增加“请问”、少量错别字；
- 产品名简称和全称。

### P2：数据量增长后的调整

当前只有数百条 QA，三字片段宽松查询成本可控。规模到数万以上后，应基于 P95/P99 和误召回率决定是否：

- 为标准问句单独存储 n-gram 字段；
- 使用业务词典补充分词；
- 加入轻量 cross-encoder reranker；
- 把 knowledge base ID 前置为 Redis TAG filter。
